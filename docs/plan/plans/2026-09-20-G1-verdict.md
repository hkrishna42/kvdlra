# G1-verdict Implementation Plan — Gate 1 Stage 1: panel prompt, harvest, verdict, Stage 2

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Take Gate 1 Stage 1 from "two pods running" to a `docs/plan/DECISIONS.md` entry that names the branch from `gate1_verdict()`, with the five-reviewer simulation run on the rendered table before anyone on the team reads it.

**Architecture:** No new statistics and no `src/` change: `kvdlra.eval.gate1` and `make gate1` already render the table and print the verdict. This lane adds (1) the panel prompt as a committed document, (2) the harvest-and-cite procedure, (3) the panel run and the DECISIONS/GATES bookkeeping, (4) the conditional Stage-2 amendment and (5) the ss2/smoke amendments that wait behind the reading. Tasks 2–5 are gated on pods finishing or on owner decisions; Task 1 runs now.

**Tech Stack:** markdown; `scripts/pod.py harvest|check`; `make gate1`; five parallel read-only opus agents dispatched by the orchestrator.

**Spec:** `prereg/gate1_tracker_swap_v2.md` §4, §6, §9, §10 and Amendments 1a/1b; `docs/plan/KICKOFF_WEEKS0-3.md` Part E ("run the five-reviewer simulation on the table alone before reading it yourself"); `docs/plan/lanes/GATES.md` §G3 and §G5; `docs/plan/ICML2027_PLAN.md` §2 Gate 1; `prereg/bf16_gist.md` §4; `docs/plan/reviews/2026-09-01/review-briefing.md` (the house format of a simulated panel).

## Global Constraints

- Forbidden words in new docs and commit messages: DLRA (as a word), BUG integrator, honest/honestly, marquee, flagship.
- The panel sees `docs/paper/tables/gate1.md` and `prereg/gate1_tracker_swap_v2.md` and nothing else (prereg §10, verbatim: "The simulation sees `docs/paper/tables/gate1.md` and this file, and nothing else — no lane report, no summary, no branch recommendation — and its output is committed beside the table. Only then is the verdict read."). The orchestrator does not open `gate1.md` before the five readings are committed.
- `gate1_verdict()` decides the branch; a reading never does. A refused family is REFUSED; records are never repaired or re-run with a knob changed.
- Records are committed by explicit path (`git add <paths>` then `git commit -o -- <paths>`); `pods.txt`, `*.raw`, `*.log`, `watchdog.pid`, `done.txt`, `status.txt` are gitignored and stay local.
- `docs/plan/STATE.md` and `docs/plan/DECISIONS.md` are append-only and only the orchestrator appends; every append is verified with `grep` afterwards.
- A launched pod's prereg is never edited in place: dated amendments only, each committed before the launch commit it governs.
- Stage 2, the ss2 pods and the smoke pod launch only under a fresh D-003 line from the owner.

```markdown
# Gate-1 panel prompt — five simulated reviewers read the Stage-1 table before the team does

## 1. Why this exists
Quote prereg/gate1_tracker_swap_v2.md §10 ("The five-reviewer simulation runs on the table before anyone reads it") and
docs/plan/KICKOFF_WEEKS0-3.md Part E's note, verbatim, with the line numbers. State the rule this document enforces:
the orchestrator dispatches five readers without having opened docs/paper/tables/gate1.md; the readings are committed
beside the table; only then is the VERDICT line read and DECISIONS appended.

## 2. What every reader gets, and nothing else
- `docs/paper/tables/gate1.md` — the table `make gate1` rendered from results/gate1_v2_stage1_{llama,qwen}/.
- `prereg/gate1_tracker_swap_v2.md` — the pre-registration, with every dated amendment appended below §11.
Forbidden inputs, named so a reader cannot drift into them: results/, docs/plan/STATE.md, docs/plan/DECISIONS.md,
docs/plan/cleanup/, docs/plan/reports/, docs/plan/SESSION_PROMPT_*.md, git log, `make gate1`, any other prereg, any
other table, the paper. A reader who needs a number the two files do not carry writes "not in the table" and moves on.

## 3. The five lenses
Each reader takes ONE lens. All five answer the same five questions (§4) through their lens.

R1 — Pre-registration compliance and statistics. Does every printed statistic correspond to one §4/§6 names — the
exact paired McNemar over the shared (seed, trial) keys, Holm at α = 0.05 over the families §6 fixes as amended
(primary retrieval, perplexity, secondary), the paired t-test, the paired bootstrap CI and the ±0.02 TOST over the 32
windows? Are the realised family sizes the pre-registered ones? Are dropped keys, error rows and refusals reported as
§4 and Amendment 1a require (REFUSED distinct from UNDECIDED; refused families out of every Holm family)? Recompute one
Holm adjustment and one TOST by hand from the printed raw values and say whether they agree. Does the VERDICT line follow
from the members by the rule exactly as §4 writes it — A/B only if BOTH families are separated from BOTH frozen and
nogist; C only if no Holm-significant fd/frozen separation exists on any task in any family AND every fd/frozen TOST
passes; otherwise REFUSED or UNDECIDED?

R2 — Mechanism. Reading isvd against frozen, random, nogist, fd and oja: where do retrieval and perplexity come from?
Does the byte-matched no-gist arm carry retrieval? Is the frozen basis as good as the tracked one? Does the fd arm
separate anywhere? Compare the pattern with the predictions §5 wrote before the run and say where the table agrees and
where it does not. What would you conclude about whether the online-tracked gist does work a frozen basis or no gist does
not?

R3 — Experimental validity. n = 24 per cell: what can and cannot be separated at that n; floor-against-floor cells
(McNemar p = 1.0 with no discordance); the `vt` rows (descriptive only — say what the table says about why); the real-
document haystacks; the pairing report; the no-gist arms' byte match; any error row; the two-family structure (one
separated family is UNDECIDED, never rounded up). What would a sceptical reviewer demand before accepting the branch?

R4 — Claims and writing. List the sentences a paper could write from this table alone, and the sentences it could not.
Say whether "the tracker is load-bearing" is writable. Name every overclaim a reviewer would attack, and the neutral
wording that survives. Note any number the table prints that a reader could mistake for a memory, throughput or baseline
claim (the table makes none).

R5 — Area chair. Read the whole table. Which branch does a fair reader infer, independent of the VERDICT line? What is
the single strongest objection? What must Stage 2 (Mistral 16K; the 32K pods) show to change or confirm it? Give a 1–10
confidence that the online-tracked gist does work a frozen basis or no gist does not, and a 1–10 confidence that the
table follows its pre-registration.

## 4. What every reader returns — one page, ≤ 60 lines, this shape
1. Numbers I read — every cell you rely on, quoted with its row and column.
2. Rule compliance as I read it — the rule clause, the members that decide it, agree/disagree with the VERDICT line.
3. The three strongest objections.
4. What I would need to see before believing the branch.
5. One-line verdict in my own words.
File: docs/plan/reviews/<YYYY-MM-DD>-gate1/R<k>-<slug>.md, where <slug> is compliance | mechanism | validity | claims | chair.

## 5. How the orchestrator dispatches it
Five Agent calls in ONE message, subagent_type general-purpose, model opus, run_in_background true, each prompt = the
preamble below + one lens from §3 + the return format of §4 + its output path. The orchestrator writes nothing about
the table into any prompt because it has not read the table. When all five have returned, the orchestrator writes
docs/plan/reviews/<YYYY-MM-DD>-gate1/meta.md (≤ 15 lines: objections raised by ≥ 2 readers; disagreements between
readers; whether R1's compliance check failed and on what), commits the directory together with the table, and only
then reads the VERDICT line and appends the Gate-1 outcome to docs/plan/DECISIONS.md.

### Preamble (verbatim in every dispatch)
You are one of five independent reviewers reading a pre-registered experiment's result table blind. You may open
exactly two files: <path to gate1.md> and <path to prereg/gate1_tracker_swap_v2.md>. Open nothing else — no results
directory, no plan or state or decisions files, no git history, no other prereg, and run no code. Treat the table as the
only evidence and the prereg as the only rule. Do not summarise the prereg back; read it to check the table against it.
Write your reading to <output path> in the five-part shape below, ≤ 60 lines, numbers quoted with their cell. Return only
the output path.

## 6. After the panel
The readings are evidence for the DECISIONS entry, not a vote: the branch is `gate1_verdict()`'s. The entry cites the
readings' path beside results/gate1_v2_stage1_{llama,qwen}/ and docs/paper/tables/gate1.md. If R1 reports a
compliance failure (a printed statistic that is not the pre-registered one), that is a harness defect to fix in a
later commit and a re-render — never a reason to read the verdict differently.
```
