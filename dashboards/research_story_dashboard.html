Can a math trick from physics simulations shrink an LLM's memory?

When a language model reads a long document, it keeps a growing scratchpad called the KV cache. This project tests whether a well-studied compression method from numerical mathematics — the BUG integrator — can keep that scratchpad small while the text streams in, without retraining the model. Ten weeks in, we have real wins, honest losses, and a precise map of where each lives.

1 · Start here: the problem

You know the KV cache exists. Here is the only other thing you need: it gets huge.

What the KV cache actually is

As a model reads text, it writes two numbers-tables for every single word it has seen: a K (key — "how can later words find me?") and a V (value — "what do I contribute when found?"). To generate the next word, the model looks back across all of these entries. That lookup table is the KV cache.

The problem: the cache grows with every word and never shrinks. For an 8-billion-parameter model reading a 32,000-word context, the cache alone is about 4 GB — per conversation. That's often more than the GPU memory left after loading the model, and it's the main reason long contexts are slow and expensive.

🗒️ Analogy: imagine taking meeting notes where you must write down every sentence anyone says, verbatim, forever — and re-read all of it before you speak. This project asks: can we keep a smart running summary instead, updated live as people talk?

2 · The idea we're testing

Two schools exist for shrinking the cache. We brought in a third tool and tested it against both.

🗑️ School 1: Throw words away ("eviction")

Keep the words the model pays most attention to, delete the rest — entirely. Methods: SnapKV, MorphKV, ExpectedAttention. Simple, cheap, and very hard to beat. But deleted is deleted: if a discarded word matters later, it's gone forever.

📉 School 2: Keep everything, roughly ("low-rank / quantize")

Store every word, but blur each entry so it takes less space. Methods: ThinK, Palu, ShadowKV, plus number-rounding (quantization). Nothing is forgotten, but everything is slightly fuzzy.

🧮 Ours: a live mathematical summary (BUG)

Keep a fixed-size summary that captures the dominant patterns across all words seen so far, and update it with each new word. The updater is the BUG integrator (Ceruti–Lubich) — a method from numerical analysis built for exactly this "track a big evolving object with a small representation" problem in physics and quantum simulations. Nobody had tried it on KV caches.

📝 The whiteboard analogy: a fixed-size whiteboard where you keep the best possible summary of the whole meeting, erasing and rewriting a little with every new sentence. "Rank" = the size of the whiteboard.

5 · The map: who wins where

Ten weeks of testing compress into one honest sentence: there is no single winner — there are regimes.

Extreme compression → BUG wins (only option)

Below ~7% memory every rival either breaks or simply cannot get that small. BUG still produces sensible text at 3.3% (135 MB instead of 4 GB), at a quality premium. If memory is the hard constraint, BUG is the only game in town.

Everyday budgets → word-deletion wins

At 10–50% memory, MorphKV/SnapKV are near-lossless on ordinary text (7.54 vs 7.62 uncompressed) — because most words genuinely don't matter later, deleting them is almost free, and eviction carries zero bookkeeping overhead.

Finding needles at 32K → ExpectedAttention wins

For "recall one exact detail from a huge document," keeping the right words verbatim beats any summary: ExpectedAttention scores 100% at 10% memory, while BUG scores 0% at every rank at 32K.

🧱 Wall 1 — the ceiling: our tracker is already ~perfect

within ~1% of the theoretical optimum

We measured BUG against the best possible summary (computed with full hindsight) and against every serious rival tracker. BUG essentially ties the optimum and beats the rivals. Consequence: no cleverer summarizer can meaningfully help — future gains must come from changing what we store, not how we track it.

🧱 Wall 2 — the floor: the whiteboard itself costs memory

85% of a tiny budget is fixed overhead

BUG must store its "whiteboard" (the basis) before it stores a single word. At generous budgets that's a rounding error; at extreme squeezes it eats 85% of the budget — while eviction pays zero overhead. That's mechanically why eviction wins the extreme regime, and why no tuning can flip it. Only removing or sharing the overhead can.

6 · The clearest win: BUG remembers what eviction forgets

Week 9's headline result. Eviction's fatal flaw is that deleted words are gone forever. We used BUG as a recovery tier: a small always-on summary sitting alongside, holding a compressed memory of everything ever seen. Then we tested: hide facts, let the eviction cache delete them, ask for them later.

🎯 1B model: eviction recalled 0 of 4 deleted facts. BUG recovered 4 of 4 — using less memory (4.02M vs 4.59M floats).
🎯 8B model, harder multi-fact test: eviction 0 of 6 → BUG 6 of 6 (needs a 1.8× memory premium at that difficulty). Confirmed on rented GPUs.

Bonus finding: BUG is also the fastest adaptive method per generated token (20.5 ms vs eviction's 26.9 ms at 8B on GPU).

7 · How we keep ourselves honest

A research result is only worth something if it survives someone trying to kill it. Built into the process:

  • Adversarial critics at every milestone. Independent review passes re-derive the numbers and hunt for overclaims before anything is called "done" (3 of 3 skeptics signed off on Weeks 8–9).
  • Public retractions. Week 4's exciting "beats state-of-the-art at 10×" turned out to be an unfair comparison (our method compressed, rivals not). We retracted it in the docs, the paper, and the README — and the honest version became the foundation for everything after.
  • A skeptic once saved a win. Week 9's recovery result was nearly filed as a failure; an adversarial reviewer spotted the test itself was flawed. Rerun properly → the project's biggest win.
  • Honest memory accounting. Every method is charged for every float it stores — including rivals' bytes "hidden" on the CPU, and including our own bookkeeping. We even fixed an error that overcharged our own method (~2–6% of budget) and reported that the fix bought no quality win.
  • Negatives are published, not buried. Weeks 5, 8, and parts of 6–7 are documented failures with measured mechanisms. They're what make the map trustworthy.
  • Engineering discipline. 248 automated tests, type-checked, reproducible seeds, every figure regenerable from committed JSON.

8 · What's next (Week 11)

Mission: teach BUG to find the needle at 32K — or prove it can't. The diagnosis is precise: a needle is a rare outlier, and outliers are exactly what summaries smear. So the plan is a hybrid: BUG keeps the compressed gist of everything, plus a tiny tier of exactly-stored "surprising" words (the machinery for spotting them already exists from Week 9).

The bar is falsifiable and pre-registered: match ExpectedAttention's 100% retrieval at ≤10% memory, or publish the negative and complete the map. A deeper mathematical brainstorm of how to get there — and beyond — lives in the companion dashboard: research_brainstorm_dashboard.html.

9 · Tiny glossary

KV cache — the model's per-word memory (Keys + Values) that grows with context length and dominates GPU memory in long chats.
Eviction — compressing by deleting whole words from the cache (SnapKV, MorphKV, ExpectedAttention are eviction methods).
Low-rank / rank — representing a big table as a combination of a few patterns; "rank" is how many patterns you allow. Bigger rank = bigger whiteboard = more faithful.
BUG integrator — a numerical-analysis algorithm (Ceruti–Lubich) for updating a low-rank summary as the underlying object evolves. The "hero" of this project. (Yes, it's really called BUG — an acronym for its two steps: Basis-Update & Galerkin.)
Oracle — the best summary theoretically possible with full hindsight (via SVD). Our impossible-to-beat yardstick.
Perplexity (ppl) — a standard "how confused is the model" score on real text. Lower is better; +5% is mildly worse, 2× is badly broken.
Needle test / RULER — hide a random code in a huge document, ask the model to retrieve it. Tests exact recall, not gist.
Pre-RoPE keys — keys captured before position-stamping. Week 2 found they compress ~2× better; a key design choice of ours.
Matched memory — every comparison holds total stored floats equal across methods, so nobody wins by secretly using more memory.
1B / 8B — the two model sizes tested (Llama 3.2 1B for cheap iteration, Llama 3.1 8B for confirmation on rented GPUs).
